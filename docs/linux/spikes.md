Host: Kubuntu 26.04.1, Plasma 6.6.6, Wayland session with XWayland (`DISPLAY=:0`, `WAYLAND_DISPLAY=wayland-0`), Electron 44.4.3, electron-builder 26.16.1, `kernel.apparmor_restrict_unprivileged_userns=0`. Run 2026-10-06 from the ext4 clone. "USER" means it needs a person at the keyboard or sudo; "CI" means the first CI run of the branch answers it.

| S14 | Does `app.commandLine.appendSwitch('ozone-platform','x11')` in the main script take effect? | **Fail → relaunch instead (Pass)** | Scratch app with the in-script switch: `getSwitchValue` returns `x11` but no X11 window exists and libwayland messages appear, i.e. Chromium had already chosen Wayland. Control run with the CLI flag `--ozone-platform=x11`: X11 window found by `xwininfo`. Chromium also pre-populates `--ozone-platform=wayland` into the switch list when it auto-selects, so `hasSwitch` cannot tell an explicit flag from the default; the raw `process.argv` can. A relaunch (`spawn(self, [...argv, '--ozone-platform=x11'])`, then `app.exit(0)`, before the single-instance lock) produced a child that got the lock, reported `switch=x11` and had an X11 window; the parent lived about 1 s. Implemented in `displayServer.ts` (`relaunchInX11IfNeeded`). Verified on the built 1.2.0 AppImage started without flags: `[display] … relaunching … in X11 mode` printed, X11 window present, relaunched process runs with `--ozone-platform=x11`. Side effect: the first AppImage runtime process stays idle (its mount stays) until the app quits, then both runtimes and mounts disappear |
